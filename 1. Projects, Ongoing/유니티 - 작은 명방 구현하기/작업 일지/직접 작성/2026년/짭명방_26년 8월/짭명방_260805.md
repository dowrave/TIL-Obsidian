## UnitEntity 구조 고치기(또팩토링;;)

### 개요

```
객체
- 컨트롤러
```

위 구조인 상태.

>[!question]
> 컨트롤러의 개별 필드나 메서드에 대한 접근은 어떻게 설정해주는 게 좋을까?
> 1. 객체 자체에 컨트롤러의 해당 프로퍼티 / 메서드에 접근하는 별도의 프로퍼티 / 메서드를 정의한다
> 2. 객체에는 정의하지 않는다

- 지금은 2개가 섞여 있는 상태임
1. **컨트롤러 자체가 `public` 게터 프로퍼티로 노출**된 상태
2. 컨트롤러의 **세부 요소들이 객체에도 구현되어 있는 상태**(객체가 인터페이스 역할)

- AI와 궁금한 거에 대해 얘기하면서 내린 임시 결론
1. 개별 컨트롤러를 `public`으로 노출하지 않는다.
2. 외부에서 필요로 하는 개별 필드/메서드는 상위 객체가 자신의 프로퍼티/메서드로 다시 감싸서 노출한다
 - **외부는 하위 서브시스템의 존재 자체를 몰라도 되고**, 상위 객체 하나만 보고 API를 사용한다.

- `Facade` 패턴이라기보다는, 각 메서드가 1:1로 하위 컨트롤러에 위임하는 구조라서 캡슐화에 더 방점을 주고 있다... 정도로만 이해하면 됨. 

- 궁금한 것들을 더 물어보고 내린 진짜 결론

- 이벤트의 경우, 중간 컨트롤러 `_status`에서 커스터 이벤트 접근자 문법으로 구현
```cs
public event Action OnDeath
{
	add => _health.OnDeath += value;
	remove => _health.OnDeath -= value;
}
```
> 단, 이렇게 구현한 경우는 `?.Invoke()`가 불가능하다는 점은 주의


### 개요 짜면서 다시 궁금해진 것들

#### Facade 패턴이 정확히 무엇인가?
- [[디자인 패턴 - 파사드(Facade)]]
- 위에서 했던 내용은 서브컨트롤러 자체를 숨겨서 강제로 단일 진입점을 만드는 것이므로, 순수 Facade보다는 캡슐화 목적의 위임이라고 보는 게 더 정확하다.


#### "Law of Demeter가 캡슐화를 약화시킨다"의 의미
- `Law Of Demeter(디미터의 원칙, 최소 지식의 법칙)`
- "낯선 사람에게 말하지 말라"
>[!note]
>- 한 메서드는 다음의 대상에게만 메시지(메서드 호출)를 보내야 한다.
>	- 자기 자신
>	- 자신의 필드
>	- 파라미터로 받은 객체
>	- 자신이 생성한 객체
>	- 위 객체들이 반환한 객체(체이닝은 안 됨)

- 예시
```cs
// Demeter 위반
float hp = unit.Controller.Health.CurrentHealth;
```
- `unit`은 `Controller`까지만 알아야 하는데, 내부의 `Health` 안의 `CurrentHealth`를 꺼내는 건 "낯선 사람의 낯선 사람"에게 말을 거는 셈이다.

- 왜 문제인가?
```cs
if (unitController.Health.CurrentHealth < unitController.Health.MaxHealth * 0.3f)
```
나중에 `HealthController = Health`를 리팩토링해서 `CurrentHealth`를 `Health` 값 객체로 바꾼다고 가정해보자.

- `Demeter` 위반 코드 
	- 필드를 직접 쓰는 모든 호출부가 깨진다. 컴파일 에러가 프로젝트 전역에서 발생함.
- `Facade`로 감싼 코드(`unitController.CurrentHealth)
	- `Facade` 내부 한 줄만 고치면 된다. 
	- `public float CurrentHealth => _health.CurrentHealth.Value` 같은 식으로.

캡슐화가 약해진다 = 내부 구현이 바뀌었을 때 `영향 범위Blast Radius`가 커진다는 의미다. 캡슐화의 본질은 정보 은닉을 통해 변경의 파급 범위를 국소화하는 것이기 때문에, 체인으로 내부 구조를 노출하면 국소화가 깨진다.

이외에도 부수적인 문제들
- 결합도 상승 : 내부 구조 `HealthController`의 존재를 알아야 하기 때문에
- 여러 곳에서 같은 체인이 반복되면 중복 코드가 늘어남
- IDE 자동 완성으로 `unit.Controller.` 까지 쳤을 때 세부 컨트롤러들이 나타나게 되는데, 정말 외부에서 써도 되는 것과 아닌 것의 구분이 안 됨 
	- 이 말은 잘 모르겠다. 쓰라고 `public`으로 노출한 게 아닌가?

#### 이전에 말했던 기준 중 어디에 해당하는가?
- 이전 답변 내용 중..
	- 컨트롤러가 **object의 구현 디테일**에 가깝고, object가 자기 상태 일관성을 지켜야 한다 → ① (게터도 숨기고 필요한 것만 래핑)
	- 컨트롤러 자체가 **object와 대등한 하나의 서브시스템**이고 외부에서 폭넓게 다뤄도 상관없다 → ② (게터만 공개)

- 이 케이스는 명확히 1번이다.
1. **개별 컨트롤러는 부품이지, 독립적인 의미를 갖는 서브 시스템이 아니다.** `Animator`처럼 "애니메이션 로직 전체를 캡슐화한 하나의 도구"가 아니라, 유닛의 상태라는 하나의 개념을 셋으로 쪼갠 것에 가깝다.
2. `_health, _stat, _buff`가 이미 `protected`로 관리되었다는 것 자체가 이미 1번 방향임
3. **상태 관리는 불변 조건이 중요하다.** 예를 들어, 쉴드 활성화 중에는 특정 버프를 못 받게 한다든가, 체력이 특정 스탯에 종속적으로 계산돼야 한다든가 하는 규칙이 생길 수 있는데, 이를 강제하려면 외부에서 하위 컨트롤러를 직접 건드릴 수 없어야 한다.

대신 **"컨트롤러는 항상 그런 구조다"라고 단정할 수는 없다.** "이동"을 구현한다고 하면, 물리 시스템, 애니메이션 파라미터 동기화, 경로 탐색 등과 얽혀서 그 자체로 하나의 독립된 서브시스템일 확률이 높은데, 이런 경우는 통째로 노출하는 것도 합리적일 수 있다.

#### 만약 규모가 더 커진다면 객체가 God Class가 될 텐데, 어떻게 분리할 것인가?
- 아래로 갈수록 더 큰 규모의 리팩토링이 된다.

##### Partial Class
- 구체적인 구현은 [[짭명방_260805#Partial Class에 대해]] 참고. 밑에 있다.
- 외부 API인 `unitStatusController.CurrentHealth`를 그대로 유지한다. 
- 클래스의 책임은 나뉘지 않지만 가독성은 확보됨.
- 지금 규모면 이 정도면 충분함.

##### 인터페이스로 부분 노출
- 외부 소비자가 여럿이고, 각자 필요한 게 다를 때 사용한다.
```cs
public interface IHealthReadable
{
    float CurrentHealth { get; }
    float MaxHealth { get; }
}

public interface IBuffReadable
{
    IReadOnlyList<Buff> ActiveBuffs { get; }
    bool HasBuff<T>() where T : Buff;
}

public class UnitStatusController : IHealthReadable, IBuffReadable, ...
```
UI의 HP바는 `IHealthReadable`만 받고, 스킬 시스템은 `IBuffReadable`을 받는 식으로 의존성을 최소화할 수 있다. 컨트롤러를 참조하는 소비자 종류가 눈에 띄게 늘어났을 때 고려하는 옵션.

##### 진짜 여러 개의 상위 객체로 분해
- 상위 객체 하나가 아니라, 역할 별로 상위 인터페이스를 여러 개 두고 유닛들이 그것을 **합성**하는 방식을 고려한다.
```cs
public class Unit
{
    public IUnitHealth Health { get; }   // 여전히 하위 구조는 숨기되, 접근 진입점을 도메인별로 나눔
    public IUnitStat Stat { get; }
    public IUnitBuff Buff { get; }
}
```
- `public`인데 `Demeter` 위반 아닌가요? : 인터페이스는 안정적인 계약이라서, 실제 구현체가 바뀌어도 영향이 없다.
> "이런 이름의 메서드가 있기만 하면 된다"라는 얘기이기 때문에, 세부 구현이 바뀌더라도 영향은 없다는 의미인 듯.

여기까지 오면 클래스가 정말 너무 커서 아무도 이해하지 못 하는 경우라고 보면 된다.

#### Partial Class에 대해
- **클래스의 정의가 여러 파일에 나뉘어져 있음을 컴파일러에게 알리는 표시**이다.
- 컴파일 시점에 같은 이름의 `partial class` 파일들을 전부 찾아 하나로 합친 뒤, 런타임 시점에는 원래부터 하나의 클래스였던 것처럼 동작한다.

- 규칙
	- 모든 조각 파일에 `partial` 키워드가 있어야 함
	- 네임스페이스와 클래스 접근 제어자가 일치해야 함
	- 필드, 메서드, 프로퍼티는 조각들 사이에 중복 정의하면 안 됨
	- 조각 파일 이름은 자유

- 파일 구조 예시
```
Scripts/
  Unit/
    UnitStatusController.cs           ← 필드 선언, 생성자, 초기화
    UnitStatusController.Health.cs    ← Health 관련 API만
    UnitStatusController.Stat.cs      ← Stat 관련 API만
    UnitStatusController.Buff.cs      ← Buff 관련 API만
```

- 코드 예시
```cs
// UnitStatusController.cs
public partial class UnitStatusController
{
    protected HealthController _health;
    protected StatController _stat;
    protected BuffController _buff;

    public UnitStatusController(HealthController health, StatController stat, BuffController buff)
    {
        _health = health;
        _stat = stat;
        _buff = buff;
    }
}
```

```cs
// UnitStatusController.Health.cs
public partial class UnitStatusController
{
    public float CurrentHealth => _health.CurrentHealth;
    public float MaxHealth => _health.MaxHealth;
    public void ActivateShield(float amount) => _health.ActivateShield(amount);
    public void DeactivateShield() => _health.DeactivateShield();
}
```

```cs
// UnitStatusController.Stat.cs
public partial class UnitStatusController
{
    public float GetStat(StatType type) => _stat.GetStat(type);
    public void AddStatModifier(StatType type, float modifier) => _stat.AddModifier(type, modifier);
    public void RemoveStatModifier(StatType type, float modifier) => _stat.RemoveModifier(type, modifier);
    public void AddStatOverride(StatType type, float overrideValue) => _stat.SetOverride(type, overrideValue);
    public void RemoveStatOverride(StatType type) => _stat.RemoveOverride(type);
}
```

```cs
// UnitStatusController.Buff.cs
public partial class UnitStatusController
{
    public IReadOnlyList<Buff> ActiveBuffs => _buff.ActiveBuffs;
    public bool HasBuff<T>() where T : Buff => _buff.HasBuff<T>();
    public T GetBuff<T>() where T : Buff => _buff.GetBuff<T>();
    public void AddBuff(Buff buff) => _buff.AddBuff(buff);
    public void RemoveBuff(Buff buff) => _buff.RemoveBuff(buff);
    public void RemoveAllBuffs() => _buff.RemoveAllBuffs();
    public void RemoveBuffFromSourceSkill(UnitSkillBase sourceSkill) => _buff.RemoveBuffFromSourceSkill(sourceSkill);
}
```

- Unity에서 참고할 점 : 
	- `MonoBehaviour`을 상속받는 경우에도 사용 가능. 
	- 파일명 = 클래스명이어야 하는 건 메인 스크립트 파일에만 해당한다.

- 리팩토링 전
```cs
public class UnitEntity : MonoBehaviour
{
    private HealthController _health;
    private StatController _stat;
    private BuffController _buff;

    public float CurrentHealth => _health.CurrentHealth;
    public void ActivateShield(float amount) => _health.ActivateShield(amount);
    public float GetStat(StatType type) => _stat.GetStat(type);
    public void AddBuff(Buff buff) => _buff.AddBuff(buff);
    // ... 등등, 지금 보여주신 코드가 UnitEntity 안에 그대로 있는 상태
}
```

- 리팩토링 후
```cs
public class UnitEntity : MonoBehaviour
{
    private UnitStatusController _status;

    private void Awake()
    {
        var health = new HealthController(/* ... */);
        var stat = new StatController(/* ... */);
        var buff = new BuffController(/* ... */);
        _status = new UnitStatusController(health, stat, buff);
    }
    
	// Health
    public float CurrentHealth => _status.CurrentHealth;
    public void ActivateShield(float amount) => _status.ActivateShield(amount);
    public void DeactivateShield() => _status.DeactivateShield();

	// ...
}
```
- 위임 체인이 `UnitStatusController` 1개 더 늘어난 셈이다. 
- 이렇게 되면 `UnitEntity`는 `UnitStatusController`를 하나만 알면 되고, 내부적으로 쪼개졌다는 사실은 `UnitStatusController` 안에만 갇혀 있게 된다.

그리고 이렇게 되면 `UnitEntity`에 구현되어 있던 위임 메서드들을 남겨놔야 하느냐 여부가 갈리는데, 
1. 유지한다 (위 예시)
2. `UnitEntity`에는 남기지 않고, 전부 `_status` 내부로 옮기고 `_status`를 `public`으로 노출한다

**규모가 커질수록 1번으로 시작해서 2번으로 수렴하는 경우가 많다.** `UnitEntity`가 계속 커지는 게 더 문제가 되는 경우가 많기 때문이다. 

##### 근데 2번으로 가면 캡슐화가 깨지는 게 아닐까?
```
// (1) 처음에 문제 삼았던 것
unitEntity.Controller.Health.CurrentHealth   // HealthController까지 노출

// (2) 옵션 B
unitEntity.Status.CurrentHealth              // UnitStatusController까지만 노출
```
- 둘 다 체이닝이라 똑같아 보이지만, 은닉의 경계가 다르다.
	1. 1번은 개별 구현의 디테일`HealthController`이 다 외부에 드러난다. 만약 `Health`에 대한 로직이 다른 방식으로 재구성되면 외부 호출부가 다 깨지게 된다.
	2. 2번은 `UnitStatusController`라는 개념적으로 안정된 단위까지 드러난다.
		- 내부의 `_health, _stat, _buff` 등이 어떻게 나뉘어 있든, 나중에 그 셋을 하나로 합치든 쪼개든, `unitEntity.Status.CurrentHealth`라는 외부 계약은 바뀌지 않는다.

따라서, **캡슐화가 깨진다기보다는 캡슐화의 단위가 재정의된 것**이다.
- 기존 : `UnitEntity` 하나가 캡슐화 경계
- 지금 : `UnitEntity` 안에 `Status, (이후에 생길)Movement, Skill` 등의 하위 캡슐화 경계들이 여러 개 생김

유니티의 `Rigidbody`, `Transform`, `Animator` 등을 생각해보면 `GameObject`는 `public` 프로퍼티로 이들을 노출하고 `gameObject.GetComponent<Rigidbody>().AddForce(...)` 처럼 접근한다. `Rigidbody`라는 단위 자체가 의미 있고 안정적인 개념적 경계이기 때문이다.

캡슐화의 약화를 주의해야 할 경우는 아래 2가지 중 하나다.
1. 노출 단위가 자주 바뀔 만큼 불안정한 구현 디테일일 때
	- `HealthController`처럼 "셋으로 쪼갠 부품" 수준이면 위험. 
	- `UnitStatusController`처럼 "유닛의 상태"라는 응집력 있는 개념이라면 상대적으로 안전.
2. 노출한 객체가 외부에서 자유롭게 변경 가능할 때
	- 보통 세터를 외부에서 접근 가능하게 구현하진 않으니까.

- 따라서, "노출하는 단위가 안정적이고 의미 있는 개념인가"를 핵심으로 보면 된다. 체이닝을 하더라도 구현 디테일까지 파고들면 위험하다.

## UnitEntity 상속받는 자식들 수정하기

### 질문
- `UnitEntity`에서 `UnitStatusController.cs`라는 클래스로 묶어서 관리했음
- 그럼 자식들에 있는 요소들도 저기에 합쳐줘야 하나? 분리해야 하나?

### 답변
- **분리하는 게 좋다.**
- `UnitStatusController`는 유닛이 살아있는 객체로서 갖는 내재적 상태이다. 반면,
	- `Deployment` - 유닛이 배치되었는가?
	- `OpAction, OpBlock, OpSkill` - `Operator`가 전투에서 어떻게 행동하는가
	- `EnemyAttack, Path, Movement` - `Enemy`가 어떻게 이동하고 공격하는가
	- `EnemySkill` - 보스만의 특수행동

- **캡슐화의 경계는 안정적이고 의미 있는 개념 단위여야 한다**가 위에서의 결론이었음.
- 이를 적용하면, **`상태`, `배치`, `행동`, `이동`은 서로 다른 책임을 갖는다. 그래서 구분**해주라는 것.

### 개요
- `UnitStatusController`에서 했던 고민을 각 상속 레벨에서 반복하면 된다.
- 판단 기준
	1. 1개 뿐이면 굳이 래퍼 클래스를 만들 필요 없이 필드로 노출
	2. 2개 이상이고 개념적으로 묶인다면 별도 래퍼 클래스로 그룹화

#### DeployableUnitEntity
- 현상태 유지. `Deployment` 1개만 있기 때문.

#### Operator
- 래퍼로 묶어준다.
- `Action/Block/Skill` 모두 전투에서의 행동이므로, `OpCombatController`로 묶어서 처리한다.

#### Enemy
- `Attack`은 묶지 않고
- `Path, Movement`는 묶는다(이동에 관한 로직이므로)

#### EnemyBoss
- `Skill` : 역시 단독이므로 묶지 않는다.

### 구현
- 리팩토링 개념이니까 언급할 게 있는 부분만 남겨둠

#### OperatorCombatController.cs
- `OperatorCombatController.cs` (루트 파일에 구현)
```cs
public partial class OpCombatController 
{
    private Operator _owner;

    private OpActionController _action;
    private OpBlockController _block;
    private OpSkillController _skill;

    public OpCombatController(OpActionController action, OpBlockController block, OpSkillController skill)
    {
        _action = action;
        _block = block;
        _skill = skill;
    }

    public void UpdateAlways()
    {
        _action.UpdateAlways(); // 공격 모션, 공격 쿨다운 갱신
        _skill.UpdateAlways(); // SP 회복, 스킬 효과 갱신, 자동 스킬의 발동
    }
}
```

- `UpdateAlways()`의 경우, `Operator.cs`에서는 이렇게 사용한다.
```cs
// Operator.cs

// 수정 전
protected override void UpdateAlways()
{
	base.UpdateAlways(); // 버프 갱신
	_action.UpdateAlways(); // 공격 모션, 공격 쿨다운 갱신
	_skill.UpdateAlways(); // SP 회복, 스킬 효과 갱신, 자동 스킬의 발동
}

// 수정 후
protected override void UpdateAlways()
{
	base.UpdateAlways(); // 버프 갱신
	_combat.UpdateAlways();
}

```

`OpCombatController`로 빼고, `OpCombatController`에서 관리되는 요소들을 묶은 형태가 됐는데, 하위 컨트롤러를 하나의 호출로 묶으면서 순서까지 결정한다. 이전까지는 단순히 컨테이너(객체) 단위에서 세부 컨트롤러의 메서드와 1:1 매칭을 한 단순 위임이었다면, 이런 식의 구현이 **퍼사드 패턴을 구현하는 본질에 가깝다.** 

또한, **순서 관리의 책임이 `Operator`에서 `OpCombatController`로 넘어가는 것도 중요**하다. 

#### Operator에서만 관리되는 스탯의 관리
```cs
public float SPRecoveryRate { get => Stat.GetStat(StatType.SPRecoveryRate); }
```
- `UnitEntity` 외에 있는 이런 스탯들은 어떻게 관리되어야 하는가?
	-> 별도로 관리할 필요 없다. **모든 스탯 요소를 `enum` 타입으로 정의했기 때문.**
	-> 그래서 `UnitStatusController.Stat`에 스탯 요소들을 프로퍼티로 다 구현해버려도 된다. 외부에서 사용할 때 `_status.GetStat()`으로 접근시키지 않게 하기 위함.

#### 상태머신 기반에서 직접 노출됐던 컨트롤러 참조
```cs
// 기존 상태머신은 이걸 봤음
private OpSkillController _skillController;
```
- 상태머신에서는 원래 컨트롤러를 바로 참조했는데, `Combat` 안으로 감추면 이것들을 어떻게 참조해야 하는가? 
- 퍼사드 패턴에서의 핵심은 **하위 시스템을 숨기는 게 아니라, 자주 사용하는 복잡한 인터페이스의 단순화**에 있다. 

- 그래서 지금까지 구현한 `OpCombatController`와 `UnitStatusController`에도 세부적으로 접근할 수 있는 컨트롤러 필드를 별도로 구현했음.

```cs
public HealthController Health => _health;
public StatController Stat => _stat;
public BuffController Buff => _buff;

public OpActionController Action => _action;
public OpBlockController Block => _block;
public OpSkillController Skill => _skill;
```

#### AttackType 관리
- 일단은 `ICombatEntity`에 공통으로 `AttackType`이랑 `AttackRangeType`을 넣고 객체에 넣는 식으로 관리하겠음
- `Status`에 넣어야 하나... `Combat`에 넣어야 하나... `ICombatEntity`라는 외부 참조도 있고 좀 복잡하다. 이 부분은 내일 작업함.

- 일단 `UnitEntity`이 공격하는 건 아니니까 `CurrentAttackType`을 넣고 싶진 않은 상황임. 근데 `FieldEffectController`에서 `_caster`가 `UnitEntity`라서 이 부분을 어떻게 처리할까가 고민. 
	- **`Operator` 및 `Enemy`부터는 `CurrentAttackType`이 구현되어 있는 상태.**
```cs
public abstract class FieldEffectController : MonoBehaviour, IPooledObject
{
    protected UnitEntity caster; // 시전자
    
    // ...   
}
```
