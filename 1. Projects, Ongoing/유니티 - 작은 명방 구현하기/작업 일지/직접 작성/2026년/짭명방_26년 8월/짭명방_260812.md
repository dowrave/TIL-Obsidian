## 먼저 할 일

### 1. `GetActionableGridPos`가 제대로 들어오지 않는 현상

#### 1. 구조 수정
- 기존 `OpActionController.cs`의 `_currentActionableGridPos` 관련 부분.
```cs
protected List<Vector2Int> _currentActionableGridPos;
public IReadOnlyList<Vector2Int> CurrentActionableGridPos => _currentActionableGridPos;

public virtual void OnDeploy()
{
	// SetActionableGridPos();
	_currentActionableGridPos = new List<Vector2Int>(GetActionableGridPos());
}

// 현재 gridPos + 회전 방향을 토대로 행동 가능한 그리드 포지션을 계산
public IReadOnlyList<Vector2Int> GetActionableGridPos()
{
	if (Owner == null) return null;
	
	List<Vector2Int> newActionableGridPos = new List<Vector2Int>(); 

	// 0,0 기준 왼쪽 방향의 행동 가능 범위
	List<Vector2Int> baseOffsets = Owner.OwnedOp.BaseActionableOffsets;

	// 0,0 기준 회전된 방향의 행동 가능 범위
	List<Vector2Int> rotatedOffsets = new List<Vector2Int>(baseOffsets
		.Select(basePos => PositionCalculationSystem.RotateGridOffset(basePos, Owner.Deployment.FacingDirection))
		.ToList());

	// 현재 gridPos 및 facingDirection을 기준으로 한 행동 가능 범위
	foreach (Vector2Int offset in rotatedOffsets)
	{
		Vector2Int inRangeGridPosition = Owner.Deployment.GridPos + offset;
		newActionableGridPos.Add(inRangeGridPosition);
	}

	return newActionableGridPos;
}

public void SetActionableGridPos(List<Vector2Int> newActionableGridPos)
{
	_currentActionableGridPos.Clear();
	foreach (var newGridPos in newActionableGridPos)
	{
		_currentActionableGridPos.Add(newGridPos);
	}
}
```

##### 제미나이 분석과 개선 방향
1. **`GetActionableGridPos()`의 의미가 애매**함 : 내부에서 계산을 수행하고 새로운 `List`를 반환하는 로직이 있기 때문.
2. `GetActionableGridPos()` 내부에서 `ToList()`로 리스트를 만들고, `newACtionableGridPos`라는 리스트를 또 만든다. 게다가 `OnDeploy()`는 리스트를 또 복사하는 등, **호출될 때마다 2~3개의 리스트가 힙 메모리에 쓰임.**
3. `SetActionableGridPos()`를 `OnDeploy()`에서 쓰지 않고 직접 할당하므로 일관성이 떨어짐

- 개선 방향
1. `_currentActionableGridPos`는 1회만 생성 후, `Clear()` 한 다음 다시 채워넣기
2. **역할 나누기** - 계산 및 갱신`Update` vs 외부 강제 주입`Set`

```cs
// 배치되지 않은 경우 - 현재 위치 / 방향을 계산해서 받음
// gridPosToHighlight = _combat.CurrentActionableGridPos;

if (!Deployment.IsDeployed)
{
	gridPosToHighlight = _combat.GetActionableGridPos();
}
else
{
	gridPosToHighlight = new List<Vector2Int>(_combat.CurrentActionableGridPos);
}

Logger.LogFieldStatus(gridPosToHighlight);
```
- 이 부분은 `CurrentActionableGridPos, GetActionableGridPos()` 등도 엮인 문제라서 같이 해결함 - 정확히 뭐가 어떤 역할을 하는지 이름만 갖고는 구분되지 않음

```cs
protected List<Vector2Int> _currentActionableGridPos = new List<Vector2Int>();
public IReadOnlyList<Vector2Int> CurrentActionableGridPos => _currentActionableGridPos;

public void Initialize(Operator op)
{
	Owner = op;
}

public virtual void OnDeploy()
{
	UpdateActionableGridPos(); 
}

// 현재 위치와 방향을 기준으로 행동 가능 범위를 계산하고 내부 상태를 갱신
public void UpdateActionableGridPos()
{
	if (Owner == null) return;

	_currentActionableGridPos.Clear();

	List<Vector2Int> baseOffsets = Owner.OwnedOp.BaseActionableOffsets; // 0,0 기준 왼쪽 방향의 행동 가능 범위
	Vector2Int currentGridPos = Owner.Deployment.GridPos;
	var currentDirection = Owner.Deployment.FacingDirection;

	// 현재 gridPos 및 facingDirection을 기준으로 한 행동 가능 범위 계산
	foreach (Vector2Int baseOffset in baseOffsets)
	{
		// 1. 방향에 맞게 오프셋 회전
		Vector2Int rotatedOffset = PositionCalculationSystem.RotateGridOffset(baseOffset, currentDirection);

		// 2. 현재 위치 기준 실제 그리드 좌표 계산
		Vector2Int inRangeGridPosition = currentGridPos + rotatedOffset;

		// 3. 캐싱 리스트에 추가            
		_currentActionableGridPos.Add(inRangeGridPosition);
	}
}

// 외부에서 행동 범위를 강제로 덮어씌워야 할 때 사용 (예시 : 스킬로 인한 버프 효과)
public void SetActionableGridPos(IEnumerable<Vector2Int> newActionableGridPos)
{
	_currentActionableGridPos.Clear();
	_currentActionableGridPos.AddRange(newActionableGridPos);
}
```

##### 추가로 하나 생각해보기
>[!question]
>- `UpdateActionableGridPos()`에서, 계산한 김에 바로 값을 반환하게 하는 건 어떤가? 에 대한 부분. 사실 원래 구현은 그쪽에 가깝기도 했다.
- 위처럼 설정하면 업데이트 후에 할당하는 코드를 이중으로 짜야 한다.
```cs
// CurrentActionableGridPos 업데이트
Combat.UpdateActionableGridPos(); 
gridPosToHighlight = Combat.CurrentActionableGridPos; 
```

>[!note]
>1. 우선 정답은 없는 이슈임. **어느 쪽을 선택하든 크게 틀린 건 아니다.**
>2. **`return` 값을 준다면 코드가 간결**해질 거임
>3. **`CQS(Command-Query Separation, 명령과 조회의 분리)`라는 프로그래밍 원칙**이 있다.
>	- 명령 : 상태를 변경하지만 값을 반환하지 않음 (void)
>	- 조회 : 상태를 반환하지만 상태를 변경하지 않음 (Get/Property)
>	- 기존 구조는 이 원칙을 잘 지켰던 셈.

- **이중으로 코드를 짜는 지금의 구조를 유지**하겠음. `return`값을 주도록 하는 편이 지금 구현에서 편할 거고 크게 이슈는 없을 것 같긴 한데, 메서드 하나가 여러 역할을 하는 게 나중에 봤을 때 더 번거로울 수도 있을 것 같아서.
