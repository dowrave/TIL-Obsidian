## `AttackType`, `AttackRangeType` 필드의 위치
- 캐릭터가 갖는 고유의 요소니까 `StatController`에 넣어야 하나? 
- 아니면 공격과 관련된 요소니까 `ActionController`에 넣어야 하나?

- **`Stat`에 넣었다.** 
- 공격 관련 로직이니 `Action`이라고 생각했지만, 판단 기준을 "무슨 로직인가?"가 아니라 "**누가** 값을 바꾸고 소비하는가"로 바꿔야 함.
- `AttackType`은 버프로 변경 가능한 스탯들을 관리하는 `StatController`의 책임 영역과 본질적으로 같은 종류의 데이터이다.
- `AttackRangeType`은 런타임에서의 변경이 없기도 하고 `StatController`가 데이터 기반의 값을 노출하는 기존 역할과도 어울린다.

- `StatController`에서의 구현
- 기존에 주저했던 이유 중 하나가 모두 `float`값으로 관리되는 데이터들만 있었기 때문이다.
```cs
    // 기본 값(데이터) <스탯 종류, 실제 값>
    private Dictionary<StatType, float> _base = new Dictionary<StatType, float>();

    // 스탯별 수정자
    private Dictionary<StatType, float> _modifiers = new Dictionary<StatType, float>();

    // 덮어쓰기용(MaxBlockCount, BlockSize) 등
    private Dictionary<StatType, float> _overrides = new Dictionary<StatType, float>();
```

**`AttackType, AttackRangeType`을 굳이 저 규칙에 맞춰서 작성하지 않아도 된다.** 외부에서 봤을 때는 초기화만 제대로 되면 되는 개념이기 때문이다.
```cs
// 공격 타입 - float로 관리되는 요소들과 별도로 관리
private AttackType _baseAttackType;
private AttackType? _attackTypeOverride; // 버프 적용 중이면 값 존재, 아니면 null
public AttackType CurrentAttackType => _attackTypeOverride ?? _baseAttackType;

private AttackRangeType _attackRangeType;
public AttackRangeType AttackRangeType => _attackRangeType;
```

그래서 위처럼 구현하고, 객체마다 다른 구현을 가져가고 있는 컨트롤러였기 때문에 저 필드들은 그에 맞춰서 데이터를 가져오면 된다.

```cs
public void InitializeOperator(OwnedOperator ownedOp)
{
	// ...
	
	_baseAttackType = ownedOp.OperatorData.AttackType;
	_attackRangeType = ownedOp.OperatorData.AttackRangeType;
}

public void InitializeEnemy(EnemyData data)
{
	// ...

	_baseAttackType = data.AttackType;
	_attackRangeType = data.AttackRangeType;
}

// 이외에도 
```

- `ICombatEntity` 구현
	- 이전에 `ICombatEntity`로 구현된 것들이 있어서, 거기서 필드값을 가져오는 경우도 있었음
	- 이 부분은 엔티티가 만족해줘야 하는 계약이므로 불필요한 중첩은 아니다. 상속만으로 해결 못 하는 경우도 있으니까.
```cs
public interface ICombatEntity
{
    public AttackType CurrentAttackType { get; }
    public AttackRangeType AttackRangeType { get; }

    void SetAttackType(AttackType type) { }
}

public class Operator : DeployableUnitEntity, ICombatEntity
{
    public AttackType CurrentAttackType => _status.CurrentAttackType;
    public AttackRangeType AttackRangeType => _status.AttackRangeType;
}
```

## Enemy 구현

### 시작 전 : StatController에 관해

>[!question]
> - int인 요소들이 float로 관리되는데, int만을 위한 딕셔너리를 또 만들어줘야 하나?

```cs
public int MaxBlockableEnemies { get => (int)GetStat(StatType.MaxBlockCount); }
public int BlockSize { get => (int)GetStat(StatType.BlockSize); }
```

이들을 포함한 요소들은 `float`로 관리되며, 이는 아래처럼 관리된다.
```cs
private Dictionary<StatType, float> _base = new Dictionary<StatType, float>();

// 및 기타 갱신 / 덮어쓰기 메서드
```


>[!note]
>1. 분리하지 않는 게 좋음
>	- 이미 잘 동작하고 있기 때문에, 별도의 `Int`들을 관리하는 메서드를 만들면 구조가 너무 복잡해짐.
>2. 대신 지금의 캐스팅 방식 `(int)`은 버림이라서, 부동소수점 오차로 인해 `2.999..`가 되는 순간 결과가 2가 될 가능성이 있다. **`Mathf.RoundToInt()` 사용**을 권장.

### 개요
```cs
// Enemy만의 기능 컨트롤러들
protected EnemyAttackController _attack;
protected PathController _path;
protected MovementController _movement;
```

1. `Path, Movement`는 강하게 결합되어 있음
	- `RotateModel()`은 경로에 의해 회전되는 방향이 설정됨
	- 최초 위치 또한 경로를 참조함
2. `Attack`은 상대적으로 독립적
	- 타겟팅, 쿨다운, 이벤트 핸들링 등은 경로, 이동 상태와 직접적인 의존이 없음.
	- 저지 관련 필드도 `Attack` 도메인에 가까움

- 따라서 어제 잡아둔 것처럼 **`Attack / Path + Movement`로 분리하는 게 맞음**

#### 애매한 지점들 정리
- `_blockingOperator` 
	- "이동 불능" 및 "공격 대상"
	- 이동이 불가능한 상태가 됐다 = `Navigation` 개념으로 봐야 하고, 공격은 그 이후에 일어나는 행동일 뿐임 
- `_targetBarricade`
	- 경로 탐색 로직의 폴백 타겟 개념이므로 100% 내비게이션 개념.
- **`EnemyBoss.SkillController`**
	- `AttackController`와 `SkillController`을 묶어서 `CombatController`로 처리함
	- **`Operator`처럼, 이 둘은 전투를 처리하는 로직**이기 때문.
	- **파사드를 묶을 때 어려운 부분은 아무래도 개념 단위로 묶으라는 내용 같다.** 수행이 부족한지 좀 정의하기 나름인 것 같다는 생각이 많이 들고 어려움.

- 그리고 클로드한테 물어봤을 때 `Enemy` 자체를 파셜 클래스로 쪼개는 방법도 보여줬다. 

- 두 방법의 장단점을 제미나이에게 물어봄
1. 컨트롤러들을 감싸는 래핑 컨트롤러 만들기
	- 장점
		- 명확한 책임 소재 
		- 안전한 상태 관리
	- 단점
		- 보일러플레이트 및 참조 변경
2. 객체 클래스 자체를 파셜로 쪼개기
	- 장점
		- 리팩토링 비용이 낮음 : 외부 호출 API를 수정할 필요가 없으니까
	- 단점 
		- God Class라는 점에는 변함없음
			- 책임의 혼재 : 클래스 자체가 가진 책임이 여전히 많음
			- 스파게티 코드 위험 : 파셜로 쪼개져 있더라도, 한 변수에서 다른 변수에 아무 제약 없이 접근하고 수정할 수 있음

- 제미나이는 **둘 중에서는 1번을 추천**하더라.
