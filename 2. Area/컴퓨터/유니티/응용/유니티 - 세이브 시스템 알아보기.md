#유니티 

- **게임 상태를 데이터로 표현해서 저장**한다.

>[!note]
>전체적인 저장 구조
>-  **저장** : 클래스 -> (직렬화) -> json/Binary -> (쓰기) -> 파일
>- **불러오기** : 파일 -> (읽기) -> json/Binary -> (역직렬화) -> 클래스

## 1. 기본 클래스와 구조
```cs
[Serializable]
public class PlayerData
{
	public int hp;
	public int gold;
	public float playTime;
}
```
- `[Serializable]` : "이 클래스를 **직렬화할 수 있는 데이터 구조**로 취급해도 된다"는 의미의 어트리뷰트. 
	- `어트리뷰트` - C# 클래스에 메타데이터를 붙이는 문법.

## 2. 직렬화(Serialization)
- 직렬화 : 메모리의 C# 객체를 저장하거나 전달할 수 있는 상태로 변환하는 것.
```
C# 객체
   ↓ Serialize
JSON / Binary
```

- 역직렬화
```
JSON / Binary
   ↓ Deserialize
C# 객체
```

### 참고) `[Serializable]`은 모든 타입에 필요한 건 아니다.
- `int, float, string` 같은 타입은 유니티의 직렬화 시스템이 기본적으로 지원하고 있다.
- **`[Serializable]` 어트리뷰트가 필요한 일반적인 상황은 개발자가 직접 구현한 일반적인 클래스에 해당함.** 


### 참고2) `[Serializable]`은 "직렬화가 가능하다"라고 알리는 역할만 한다.
- 위 어트리뷰트 없이 `JsonUtility.ToJson(new PlayerData())`를 한다면, 유니티의 직렬화 대상으로 인식되지 않아서 유의미한 JSON 데이터가 나오지 않는다.
- 그리고 어트리뷰트를 붙였다 = 데이터로 저장된다가 아니라, `JsonUtility.ToJson()` 등의 **직렬화 메서드로 직접 직렬화를 해줘야 저장**되는 개념이다. 

## 3. 코드로 보는 저장 / 읽기 과정
- 저장
```cs
// 1. 객체 → JSON 문자열
string json = JsonUtility.ToJson(data);

// 2. JSON 문자열 → 파일
string path = Path.Combine(Application.persistentDataPath, "save.json");

// 3. 파일로 저장
File.WriteAllText(path, json);
```

- 읽기
```cs
string path = Path.Combine(
    Application.persistentDataPath,
    "save.json"
);

if (File.Exists(path))
{
    string json = File.ReadAllText(path);

    PlayerData data = JsonUtility.FromJson<PlayerData>(json);

    Debug.Log(data.hp);
    Debug.Log(data.gold);
}
```

## 4. JsonUtility의 직렬화 규칙

- 기본 : **`public` 필드**는 기본적으로 직렬화 대상이 된다.
	- 단, `[SerializeField]`를 쓰면 `public`이 아니어도 직렬화 가능하다. 

- 주의 사항
	- `JsonUtility`는 유니티의 직렬화 시스템을 기반으로 하므로, 아무 C# 객체나 자유롭게 JSON으로 전환해주는 라이브러리는 아니다.

- 제한 사항
	- 직렬화 지원
		- `public`
		- `[SerializeField]`
		- `int, float, string` 등의 기본 타입
		- 배열
		- `List<T>`
		- `[Serializable]` 클래스
	- 직렬화 제한 / 미지원
		- `Dictionary<TKey, TValue>`
		- 프로퍼티
		- 일반적인 `private` 필드
		- 복잡한 C# 객체 구조 일부

> 대부분 경험적으로 아는 요소일 거임. 

## 5. MonoBehaviour로 세이브 데이터를 구현하지 않는 이유

1. 불필요한 데이터와 직렬화 오류 방지
	- `MonoBehaviour`는 유니티 엔진과 강하게 연결되어 있다. 내부에는 `Transform`, `GameObject 참조`, 엔진 내부 콜백 데이터 등 저장할 필요가 없는 많은 데이터가 있어서, 저장하려 하면 파일 크기가 비정상적으로 커지거나 직렬화 중 순환 참조 오류가 발생한다.
2. JsonUtility의 설계 목적
	- 엔진을 직렬화하는 게 아니라, 개발자가 정의한 `순수한 데이터 구조(POCO: Plain Old C# Object)` 처리에 최적화되어 있다. 
3. 데이터 관리의 편의성
	- 저장해야 할 핵심 데이터만 `PlayerData`라는 독립 클래스로 묶는다면 이후 데이터 구조를 바꾸거나 세이브 파일의 암호화에서 안전하게 작업할 수 있다. 

**로직(MonoBehaviour)와 데이터(Data 클래스)를 따로 분리하는 것이 핵심.**


## 6. PlayerPrefs에 관해 - 간단한 경우 I/O역할 대체 가능
- `JsonUtility`가 직렬화 / 역직렬화를 맡았다면
- `PlayerPrefs`는 **`JsonUtility`가 만들어준 문자열을 지정한 키값으로 저장한다.**

```cs
// 저장
string json = JsonUtility.ToJson(playerData);

// File.WriteAllText(path, json)을 대신함
PlayerPrefs.SetString("SaveData", json);
PlayerPrefs.Save();

// 불러오기
if (PlayerPrefs.HasKey("SaveData"))
{
	string savedJson = PlayerPrefs.GetString("SaveData");
	PlayerData loadedData = JSonUtility.FromJson<PlayerData>(savedJson);
}
```

- `JsonUtility + PlayerPrefs`의 장단점
	- 장점 : 복잡한 파일 경로를 신경 쓸 필요 없이 코드가 매우 짧아짐
	- 단점 : 데이터 용량이 커지면 `PlayerPrefs`에 무리가 갈 수 있음

### 단점에 관해
- `PlayerPrefs`는 원래 **환경 설정을 저장하라고 만든 기능**이라, 세이브 데이터로 쓴다고 하면 아래의 한계가 있다.
1. 데이터를 운영체제의 레지스트리(Windows)나 공용 설정 파일(모바일)에 저장한다. 여기서 수천 줄짜리 JSON이 들어가면, 저장/불러오기에서 렉이 발생할 수 있음.
2. 보안 / 조작에 취약함 : 저장 위치가 알려져 있고 평문으로 저장하므로, 유저가 에딧하기 너무 쉬운 구조.
3. RPG 게임처럼 세이브 슬롯 1, 2, 3을 만든다든가, 스팀 클라우드 연동, 유저 간 세이브 파일 공유 등을 하려면 물리적인 파일`save_slot1.json`로 관리해야 한다. `PlayerPrefs`는 이런 유연한 관리가 불가능하다.
