## 검색의 이해

- 저장된 자료(배열, 리스트, 트리 등) 중, **원하는 키값을 가진 항목**을 찾아내는 작업. 
- 자료가 어떻게 저장되어 있는지(정렬 여부, 자료구조 형태)에 따라 쓸 수 있는 검색 방법과 효율이 달라짐.
- 검색 효율 : 시간복잡도(몇 번 비교하는가)로 평가

- 정렬 여부는 트레이드오프다.
	- 정렬해두면 검색은 빨라지지만(이진 검색 $O(\,n log\,n)$)
	- 삽입 / 삭제할 때마다 정렬 상태를 유지하는 비용이 든다.
- 해싱은 비교를 없애는 접근법에 가깝다. 키값으로 저장 위치를 직접 계산해서 이론상 $O(1)$ 검색을 노림.

## 순차 검색 (정렬되지 않은 자료)

### 정렬 X 순차 검색 개념
- 정렬되지 않은 자료를 검색하는 로직.
- **저장 순서에 무관하게, 첫 번째 항목부터 마지막까지 비교하며 찾는 가장 단순한 검색 방법.**
- 별도의 정렬이나 부가 자료 구조가 필요 없다.
- 최선 : $O(1)$ (첫 원소)
- 평균 / 최악 : $O(n)$ 
	- 정렬 X이므로, 중간에 더 이상 없다고 판단할 근거가 없음(정렬 O와의 핵심 차이점)
### 정렬 X 순차검색 알고리즘
1. 배열의 첫 번쨰 원소부터 순서대로 순회한다.
2. 현재 원소가 찾는 키값과 같은지 확인한다.
3. 같으면 해당 인덱스를 반환 후 종료한다.
4. 끝까지 못 찾으면 실패값 `-1`을 반환한다.

### 정렬 X 순차검색 C# 구현
```cs
public class SequentialSearch
{
	// 정렬되지 않은 배열에서 key를 순차적으로 검색
	// 찾으면 인덱스, 못 찾으면 -1
	public static int Search(int[] arr, int key)
	{
		for (int i = 0; i < arr.Length; i++)
		{
			if (arr[i] == key)
				return i;
		}
		return -1;
	}
}
```
- 값이 일치하는 즉시 반환해서 불필요한 비교를 줄인다.
- 실패를 확정하려면 끝까지 순회해야 한다. 

단순한 로직이므로 예제는 필요하지 않을 것 같아 생략.

## 순차 검색(정렬된 자료)

### 정렬 O 순차검색 개념
- **자료가 오름차순**이라는 전제로, **검색 실패를 더 일찍 확정**할 수 있게 개선.
- **현재 비교 중인 원소가 찾는 키값보다 크면 정렬 순서상 그 뒤에는 키값이 존재할 수 없으니 순회를 멈춘다.**
- 정렬 X와의 차이점 
	- 찾는 항목이 존재하지 않을 때의 평균 비교 횟수가 줄어든다.
- 최악의 경우(키값이 마지막 원소이거나 배열보다 큰 경우)의 시간 복잡도는 여전히 $O(n)$

### 정렬 O 순차검색 알고리즘
1. 배열의 1번째 원소부터 순서대로 순회한다.
2. 현재 원소가 키값과 같으면 그 인덱스를 반환하고 종료한다.
3. 현재 원소가 키값보다 크면 뒤에도 없다는 뜻이므로 즉시 실패를 반환하고 종료한다.
4. 현재 원소가 키값보다 작으면 다음 원소로 이동해 2번부터 반복한다.
5. 끝까지 도달하면 실패를 반환한다.

### 정렬 O 순차검색 C# 구현
```cs
public class SortedSequentialSearch
{
	// 오름차순 정렬된 배열에서 key를 검색, 인덱스를 반환
	public static int Search(int[] arr, int key)
	{
		for (int i = 0; i < arr.Length; i++)
		{
			if (arr[i] == key)
				return i;
			if (arr[i] > key)
				return -1; // 이미 key보다 큰 값이 나타났으므로 더 이상 찾을 수 없음
		}
		
		return -1; // 못 찾은 경우
	}
}
```
- 찾는 값이 실제로 배열에 없을 때, 끝까지 순회하지 않고도 실패를 확정할 수 있다는 점이 핵심 개선점이다. 

## 색인 순차 검색

### 색인 순차 검색 개념
- 정렬된 자료를 몇 개의 블록으로 나눈 뒤, 각 블록을 대표하는 색인 테이블을 별도로 만드는 개념.
- 검색 시 먼저 색인 테이블에서 키값이 속한 블록을 찾고, 그 블록 안에서만 순차 검색을 수행한다.
	- 즉, 전체 순차 검색 -> "해당 블록 순차 검색"으로 범위를 줄이는 것.
- 이진 검색만큼 빠르지 않으나, 순수 순차 검색보다는 비교 횟수를 줄일 수 있다.
- 색인 테이블 크기와 블록 크기 사이에 트레이드 오프가 있다.
	- 블록 크기를 줄이면 블록 내 검색은 빨라지지만 색인 테이블이 커져 1단계 검색 비용이 늘어난다.
	- 역도 마찬가지.

### 색인 순차 검색 알고리즘
1. 색인 테이블을 순차/이진 검색해서 키값이 속할 수 있는 블록을 찾는다.
	- 보통 각 블록의 마지막값(최댓값)을 색인 테이블에 저장한 후, 키값 이상인 첫 번째 색인 항목을 찾는다.
2. 해당 색인 항목이 가리키는 블록의 시작 위치를 구한다.
3. 그 블록 범위 안에서만 순차 검색을 수행한다.
4. 블록 안에서 키값을 찾으면 인덱스를 반환한다.
5. 블록 안에 없으면 실패를 반환한다.

### 색인 순차 검색 C# 구현
```cs
public class IndexedSequentialSearch
{
	// 오름차순 정렬 배열을 blockSize 단위로 나누고, 
	// 각 블록의 마지막 값으로 색인 테이블을 만들어 검색
	public static int Search(int[] arr, int key, int blockSize)
	{
		int blockCount = (arr.Length + blockSize - 1) / blockSize;
		
		// 1. 색인 테이블(=각 블록의 마지막 값) 순차 검색으로 블록 찾기
		int targetBlock = -1;
		for (int b = 0; b < blockCount; b++)
		{
			int lastIdx = Math.Min((b + 1) * blockSize, arr.Length) - 1; // 하단 설명 참고
			if (arr[lastIdx] >= key)
			{
				targetBlock = b;
				break;
			}
		}
		
		if (targetBlock == -1)
			return -1; // 어떤 블록의 마지막 값도 key보다 작으므로 존재하지 않음
			
		// 2. 해당 블록 범위 안에서 순차 검색
		int start = targetBlock * blockSize;
		int end = Math.Min(start + blockSize, arr.Length);
		for (int i = start; i < end; i++)
		{
			if (arr[i] == key)
				return i;
		}
		return -1;
	}
}
```
- `blockSize`는 설계 시점에 임의로 정하는 파라미터다. 
	- 위에서 블록의 크기와 색인 테이블의 크기 간에 트레이드오프가 있다고 했는데, 이를 최소화하는 이론적인 기준이 있다.
	- 결론부터 말하면 **`blockSize`는 총 데이터 크기의 제곱근`(n)^(1/2)` 값이 이론적 기준**임.
		- 전체 자료 갯수를 $n$, 블록 크기를 $b$ 라고 하면 
			- 색인 테이블 검색 비용 = `n/b`
			- 블록 내 검색 비용 = `b`
			- 이 둘의 **검색 비용이 최소가 되는 지점**은 미적분으로 구하면 $b=\sqrt{n}$이다. 
			- 이 때의 총 비교 횟수가 약 $2\sqrt{n}$으로, 순수 순차 검색의 $O(n)$보다 훨씬 적다.
	- 실제로는 캐시 라인 크기나 디스크 블록 크기 등의 하드웨어적 요인에 맞춰서 조정하기도 한다. 

- `int lastIdx = Math.Min((b + 1) * blockSize, arr.Length) - 1;`
	- `(b + 1) * blockSize` 
		- 블록 `b`에 들어가는 원소 갯수.
		- 결과적으로는 `블록 b의 마지막 인덱스 +  1`를 의미함.
	- `arr.Length`를 넣는 이유
		- 마지막 블록이 `blockSize`보다 작을 수 있기 때문. 
			- 예시 : `[1, 2, 3]`, `blockSize = 2`라면 `b = 1`일 때의 블록은 `[3]`밖에 없지만 `(b + 1) * blockSize = 4`로 인덱스를 초과한다. 반면 `arr.Length = 3`임.
	- `-1`은 양쪽이 모두 마지막 인덱스를 1씩 초과하니까 보정


#### 색인 순차 검색 예제
- [1, 3, 5, 7, 9, 11, 13, 15], `blockSize = 4`(임의 설정), `key = 11`을 찾고자 한다면

1. 블록 탐색

|  b  | lastIdx | arr[lastIdx] >= key |
| :-: | :-----: | :-----------------: |
|  0  |    3    |    false(7>=11)     |
|  1  |    7    |    true(15>=11)     |
2. 순차 검색
- `start = targetBlock * blockSize = 1 * 4 = 4`
- `end = Math.Min(8, 8) = 8`
- 이후는 순차 검색이므로 생략.

## 이진 검색

### 이진 검색 개념
- 정렬된 자료에서 **매 비교마다 검색 범위를 절반씩 줄여나가는 검색** 방법.
- 중간 원소와 키값을 비교, 키값이 더 크면 오른쪽 절반만, 더 작으면 왼쪽 절반만 다시 검색 대상으로 삼는다.
- 정렬된 자료 순차 검색은 조기 종료를 해도 최악 $O(n)$이지만, **이진 검색은 범위 자체를 절반씩 줄이므로 $O(log\,n)$이다.** 색인 순차검색$O(\sqrt{n})$보다 빠르다.
- 전제 조건 : **자료가 반드시 정렬**되어 있어야 하고, **배열**처럼 중간 위치에 임의 접근할 수 있어야 함. 

### 이진 검색 연산
1. 검색 범위를 배열 전체 `low = 0`, `high = arr.Length - 1`로 설정
2. `low > high`이면 검색 범위가 비어있다는 의미 - 실패를 반환 후 종료
3. `mid = (low + high) / 2`를 구한다.
4. `arr[mid] = key`라면 `mid` 반환 후 종료
5. `arr[mid] > key`라면 왼쪽 절반에 정답이 있으므로 `high = mid - 1`로 갱신 후 2번부터 반복
6. `arr[mid] < key`라면 오른쪽 절반에 정답이 있으므로 `low = mid + 1`로 갱신 후 2번부터 반복

### 이진 검색 C# 구현
```cs
public class BinarySearch
{
	// 오름차순 정렬된 배열에서 key를 이진 검색
	// 찾으면 인덱스, 못 찾으면 -1을 반환
	public static int Search(int[] arr, int key)
	{
		int low = 0;
		int high = arr.Length - 1;
		
		while (low <= high) // low > high는 검색 조건이 비어있다는 의미
		{
			int mid = (low + high) / 2;
			
			if (arr[mid] == key)
				return mid;
			else if (arr[mid] > key)
				high = mid - 1;
			else
				low = mid + 1;
		}
		
		return -1;
	}
}
```
- 반복문으로 인덱스만 수정하는 식으로 구현된다. 재귀도 없고 배열의 복사도 없다. 
- **정렬, 임의 접근이라는 두 전제가 $O(\,log\,n)$을 만든다.** 
	- 연결 리스트처럼 중간 원소에 삽입할 수 없는 구조는 이 이점을 살릴 수 없다.

## 이진 트리 검색

### 이진 트리 검색 개념
- 이진 탐색 트리(BST)에서 루트부터 시작해 키값과 비교하며 좌, 우로 내려가는 검색 방법
- 배열 기반 이진 검색과 아이디어는 같다. 정렬된 배열 대신 트리 구조 자체가 분할을 미리 반영하고 있다.
- 트리 구조에 성능이 영향을 받는다. 균형 잡힌 트리일 경우 $O(log \, n)$, 편향된 트리(최악)는 $O(n)$이다. 
	- 그래서 같은 배열이더라도 트리에 넣는 순서에 따라 성능이 갈릴 수 있다.

### 이진 트리 검색 연산
1. 현재 노드를 루트로 설정한다.
2. 현재 노드가 없으면`null` 검색 실패로 종료한다.
3. 현재 노드의 값이 키값과 같으면 그 노드를 반환하고 종료한다. 
4. 키값이 현재 노드의 값보다 작으면 현재 노드를 왼쪽 자식으로 옮기고 2번부터 반복
5. 키값이 현재 노드의 값보다 크면 현재 노드를 오른쪽 자식으로 옮기고 2번부터 반복

```cs
public class TreeNode<T>
{
	public T Data;
	public TreeNode<T> Left;
	public TreeNode<T> Right;
	
	public TreeNode(T data)
	{
		Data = data;
	}
}

public class BinarySearch
{
	// 이진 탐색 트리에서 Key를 검색, 찾으면 해당 노드, 못 찾으면 null 반환
	public static TreeNode<int> Search(TreeNode<int> root, int key)
	{
		TreeNode<T> current = root;
		
		while (current != null)
		{
			if (current.Data == key)
				return current;
			else if (key < current.Data)
				current = current.Left;
			else
				current = current.Right;
		}
		
		return null;
	}
}
```
- 이진 검색과 BST 검색은 $O(log\,n)$으로 공식은 같아 보이나, 전제가 다르다는 점만 짚고 넘어가자.
	- 이진 검색 : "정렬"된 "배열"
	- BST 검색 : 균형 여부, 편향일 경우 $O(n)$이 된다.
		- 트리에 넣는 순서에 따라 성능이 갈릴 수 있다.

#### 예시
- 텍스트로만 풀어봄.
	- [1, 2, 3, 4, 5]가 순서대로 삽입된 경우 모든 노드가 오른쪽 자식으로 가는 편향 트리가 만들어진다.
		- 5를 찾기 위해선 모든 데이터를 뒤지는 $O(n)$이 됨.
	- 반면 [3,2,1,4,5] 순으로 넣는다면 왼쪽부터 1(-2 2 3 4 5 형태가 나옴.
		- 여기서 5를 찾기 위해선 3, 4, 5 순으로 들어가면 된다. 이게 $O(log\,n)$



## 해싱

### 해싱 개념
- **키값을 `해시 함수Hash Function`에 입력해서 나온 결과값을 배열(해시 테이블)의 인덱스로 직접 사용해 저장/검색**하는 방식. 
- 키값으로 위치를 계산해서 바로 찾아가는 방식으로, "비교하는" 방식과 접근 자체가 다르다.
- **계산이 충돌 없이 항상 성공한다면 이론적으로 $O(1)$ 검색이 가능**하다.

- 해싱의 핵심은 "비교를 몇 번만에 끝낼 수 있는 위치 계산을 어떻게 설계하는가"가 관건이다. 이후의 항목들은 전부 "계산이 완벽할 수는 없다"는 전제 하에 그 불완전함을 어떻게 다루는가에 대한 내용.

### 해싱 관련 용어

- **동거자(synonym)** 
	- 서로 다른 키값인데도 같은 해시 주소(홈 주소)로 계산되는 키들의 관계.
	- 해시 함수가 이 둘을 서로 구분하지 못했다는 의미.
- **충돌(collision)**
	- 서로 다른 키가 같은 해시 주소로 계산되어서 저장되려는 위치가 이미 다른 키로 채워진 상황.
	- 동거자 관계의 키들이 저장을 시도할 때 발생하는 사건이다.
- **키값 밀도**
	- 실제로 사용되는(테이블에 저장되는) 키의 갯수를, 그 키가 가질 수 있는 전체 값의 범위(가능한 키 공간의 크기)로 나눈 비율.
	- 해시 테이블 설계 이전에 자료 자체가 갖는 특성.
- **적재 밀도(load factor)**
	- 실제로 저장된 레코드 수를 해시 테이블이 가진 전체 버킷(슬롯) 수로 나눈 비율.
	- 테이블이 꽉 찬 정도를 나타내며, 값이 높아질수록 충돌 확률이 커진다.

1. 동거자는 관계, 충돌은 사건이다. "동거자"라는 말은 충돌 이전에도 성립할 수 있는 정적인 관계.
2. **적재 밀도는 설계자가 테이블 크기를 여유 있게 잡는 정도에 따라 어느 정도 통제할 수 있지만, 키값 밀도는 자료 자체의 성질이라 설계로 바꿀 수 없다.** 
	- 그래서 실무에서는 보통 적재 밀도를 일정 수준(0.7 ~ 0.8 이하)로 유지하도록 테이블 크기를 조정하는 식으로 충돌을 방지한다. 

### 해시 함수 1. 계산 함수, 중간 제곱함수, 승산 함수

#### 해시 함수 개념
- 키값을 입력받아 테이블 크기 범위 안의 주소(인덱스)로 변환하는 함수.
- 키들을 테이블 전체에 고르게 분산시켜 충돌을 최소화해야 한다. 

- 참고
	- 아래의 예제들은 `int key`를 쓰고 있다.
	- 딕셔너리를 예로 들면 다양한 타입을 `key`로 쓸 수 있는데, C#의 모든 객체는 기본적으로 `GetHashCode()`를 갖고 있다. 이게 `int`값을 반환함.
	- 즉, `임의 타입의 키 -> GetHashCode() -> int -> HashFunction() -> 실제 배열 인덱스`라는 이중 변환을 거친다. 
	- `GetHashCode()`의 동작을 다루진 않는다. C# 런타임 내부 구현으로, 해시 함수랑은 다른 개념이기 때문.
		- 대충 문자열이라면 문자들의 조합을, 커스텀 클래스라면 필드 조합을 바탕으로 계산이 들어가는 방식. 

#### 계산 함수
- 키값을 테이블 크기로 나눈 나머지를 주소로 사용하는 **가장 단순하고 널리 쓰이는 방식.**
- **테이블 크기를 소수로 잡으면 분포가 더 고르게 되는 경향**이 있어서 실무에서 흔히 쓰인다.
- 구현이 가장 간단하지만, 키값에 특정 패턴(특정 수의 배수 등)이 있을 때 분포가 나빠질 수 있다. 그래서 테이블 크기를 소수로 잡는 관행이 생겼다.
##### 계산 함수 C# 구현
```cs
// 계산 함수(제산 함수) - 가장 널리 쓰이는 기본형
public static int DivisionHash(int key, int tableSize)
{
	return key % tableSize;
}
```

- 충돌 예시
	- `10, 17, 24`, `tableSize = 7`
	- 7로 나누면 모두 나머지가 3인 패턴. 

#### 중간 제곱 함수
- 키값을 제곱한 뒤, 그 결과값의 중간 부분 몇 자리를 취해 주소로 사용하는 방식.
- 제곱한 값의 중간 자리는 키값의 모든 자릿수 영향을 골고루 받기 떄문에, 키값 일부만 보고 주소를 정하는 것보다 더 고르게 분산되는 경향이 있다.
- 비트 연산으로 더 효율적으로 처리하기도 한다.

```cs
// 중간 제곱 함수 - key^2의 중간 자리 일부를 주소로 사용(여기선 가운데 두 자리)
public static int MidSquarehash(int key, int tableSize)
{
	long squared = (long) key * key;
	string s = squared.ToString().PadLeft(4, '0');
	int mid = s.Length / 2;
	string middleDigits = s.Substring(mid - 1, 2); // 가운데 두 자리 추출
	int extracted = int.Parse(middleDigits);
	return extracted % tableSize;
}
```

##### 중간 제곱 함수 예시
- `key = 44`
	- `44^2 = 1936`, 4자리이므로 가운데 두 자리를 뽑으면 `93`
- `key = 45`(바로 옆 숫자)
	- `45^2 = 2025`, 가운데 두 자리는 `02`
	- 값 차이가 1밖에 안 나지만 중간 자리가 크게 달라진다. 


#### 승산 함수
- 키값에 0과 1 사이의 상수를 곱한 뒤, 결과의 소수 부분만 취해서 테이블 크기를 곱해 주소를 얻는 방식
- 계산 함수와 달리 테이블 크기가 소수가 아니더라도 비교적 고른 분포를 얻을 수 있다.
```cs
// 승산 함수 - key * A의 소수 부분에 tableSize를 곱해 주소 계산
public static int MultiplicationHash(int key, int tableSize)
{
	double A = 0.6180339887; // 황금비의 소수 부분을 흔히 쓴다.
	double val = key * A;
	double fractional = val - Math.Floor(val);
	return (int)(tableSize * fractional);
}
```

### 해시 함수 2. 접지 함수

- 키값의 **자릿수가 테이블 주소 범위보다 훨씬 클 때, 키값을 몇 개의 부분으로 나눈 뒤 그 부분들을 더하거나 결합해서 주소를 만드는 방식.**
- `key % tableSize`를 그대로 적용하면 특정 자릿수(주로 마지막 자릿수)의 영향을 크게 받는 경우가 있는데, 접지 함수는 키값을 여러 조각으로 나누고 더해서 자릿수 전체가 결과에 골고루 반영되도록 한다.
- 나누는 방식(그대로 더하는가 vs 일부를 뒤집어서 더하는가)에 따라 이동 접지와 경계 접지로 나뉨.

- 조각을 나누는 기준 : **테이블 크기를 표현하는 데 필요한 자릿수**에 맞춘다.
	- 테이블 크기가 100 이하 (0 ~ 99, 2자리) - 2자리씩 자르는 게 자연스러움(조각 하나가 0 ~ 99 범위 내에 있기 때문)
	- 테이블 크기가 1000 이하 - 3자리씩 자르는 게 자연스러움
	- 아래 예제들은 2로 설정.
#### 이동 접지 함수
- 키값을 정해진 자릿수 단위로 잘라 나눈 뒤, 그 조각들을 그대로 같은 자리끼리 더하는 방식.
- 구현이 단순하고 계산 비용이 적다.

```cs
// 이동 접지 : n자리씩 나눠서 그대로 더함, 여기서는 n = 2
public static int ShiftHolding(int key, int tableSize)
{
	string s = key.ToString();
	int sum = 0;
	for (int i = 0; i < s.Length; i += 2)
	{
		string chunk = i + 2 <= s.Length ? s.Substring(i, 2) : s.Substring(i);
		sum += int.Parse(chunk);
	}
	return sum % tableSize;
}
```

- 예시 : `123456`을 두 자리씩 잘랐다고 가정
	- `12`, `34`, `56`, 모두 더하면 `102`, `tableSize`로 나머지 연산.

#### 경계 접지 함수
- 키값을 조각으로 나누고, 짝수/홀수번째 조각을 **경계(접히는 지점)를 기준으로 뒤집어서 더하는 방식.** 
- 종이를 접듯이 조각을 반대 방향으로 겹쳐 더해서 경계 접지다.
- 조각을 뒤집어서 더하므로 이동 접지보다 자릿수 간의 상쇄(서로 다른 키인데 더한 결과가 우연히 같아지는 경우)가 줄어드는 경향이 있음.
```cs
// 경계 접지 : 2자리씩 나눈 뒤, 짝수 번째 조각은 뒤집어서 더함
public static BoundaryFolding(int key, int tableSize)
{
	string s = key.ToString();
	int sum = 0;
	int chunkIndex = 0;
	
	for (int i = 0; i < s.Length; i += 2)
	{
		string chunk = i + 2 <= s.Length ? s.Substring(i, 2) : s.Substring(i);
		
		// 홀수번째 조각은 뒤집는다.
		if (chunkIndex % 2 == 1)
		{
			char[] arr = chunk.ToCharArray();
			Array.Reverse(arr);
			chunk = new string(arr);
		}
		
		sum += int.Parse(chunk);
		chunkIndex++;
	}
	
	return sum % tableSize;
}
```

- 예시 : `123456`을 두 자리씩 잘랐다고 가정
	- `12`는 그대로, `34`는 뒤집어서 `43`, `56`도 그대로
	- 12 + 43 + 56 = 111
	- 이동 접지와 최종 합이 달라졌다. 이 차이가 곧 어느 정도까지 **자릿수를 뒤섞어 분산시키는가**의 차이.

### 해시 함수 3. 숫자 분석 함수, 진법 변환 함수
- 키값들의 **분포를 미리 살펴본 다음 그에 맞춰 주소를 뽑는 자리를 정하는 공통점**이 있다.
#### 숫자 분석 함수

- 저장될 **키 값들 전체를 미리 훑어서 각 자릿수별로 숫자가 얼마나 골고루 분포되어 있는지를 분석**하고, **분포가 편중된 자릿수는 버리고 비교저 고르게 분포된 자릿수들만 골라 조합**해 주소를 만드는 방식.
	- 예시) 사원번호처럼 앞자리 몇 개가 모든 키에서 똑같은 값이라면, 그 자릿수는 주소 계산에 도움되지 않기 때문에 제외하고 나머지 자릿수만 쓴다.
- **사전 분석 결과를 외부에서 전달받는 구조**로, **분석 자체는 함수 외부**에서 이뤄진다. 
	- 즉, 미리 자료를 볼 수 없는 상황(실시간으로 키가 들어오는 상황)에는 적용하기 어렵다. 
	- 계산 함수, 승산 함수와의 차이점. 이들은 키값을 보고 즉시 계산하니까.

```cs
// 숫자 분석 함수 - "미리 정해둔" 쓸모 있는 자릿수 위치만 뽑아 조합
public static int DigitAnalysisHash(int key, int tableSize, int[] usefulDigitPositions)
{
	string s = key.ToString().PadLeft(6, '0');
	string extracted = "";
	foreach (int pos in usefulDigitPositions)
	{
		extracted += s[pos];
	}
	
	return int.Parse(extracted) % tableSize;
}
```

#### 진법 변환 함수
- 키값을 원래 진법이 아닌 다른 진법(11, 13진법 등 테이블 크기와 서로소이거나 소수인 진법)으로 변환한 뒤, 그 결과를 다시 10진수로 해석해서 주소를 얻는 방식.
- 진법을 바꾸면서 자릿수 올림이 발생하므로, 원래 키값에선 잘 드러나지 않던 자릿수 간의 차이가 결과값에 더 크게 반영되는 효과가 있다.
```cs
public static int RadixTransformHash(int key, int tableSize, int radix)
{
	// key의 각 10진수 자릿수를 radix 진법의 자릿값인 것처럼 재구성
	string s = key.ToString();
	long value = 0;
	foreach (char c in s)
	{
		int digit = c - '0'; // char이지만 유니코드 정수이며 0~9가 붙어있어 이런 연산이 가능
		value = value * radix + digit; // radix 진법으로 다시 조립
	}
	return (int)(value % tableSize);
}
```
- 10진수 자릿수를 유지한 채 각 자리의 무게만 `radix`로 바꿔서 재계산한다. **실제 진법 변환기와는 다른 형태**로, **자릿값을 재해석한다는 아이디어**만 보여주는 코드.

- 예제 추적 - `key = 123, radix = 11`이라면
	- `c = '1'` => `value = 1`
	- `c = '2'` => `value = 1 * 11 + 2 = 13` 
	- `c = '3'` => `value = 13 * 11 + 3 = 146`
	- `123 -> 146`이 된 것처럼, 진법 변환이 값을 퍼뜨리는 효과가 있다.

### 해시 함수 4. 비트 추출 함수
#### 비트 추출 함수
- 키값을 **이진수(비트 열)로 표현했을 때, 그 중 몇 개의 비트 위치만 뽑아서 그 비트들을 조합**해 주소로 사용하는 방식.
- 계산 함수나 접지 함수처럼 산술 연산을 하지 않고, 비트 단위로 직접 골라내므로 연산 비용이 매우 낮다. 
- 어떤 비트 위치를 뽑을지는 테이블 크기에 맞춰 미리 정해둔다.
	- 테이블 크기가 `2^5 = 32`라면 5비트만 있으면 충분하므로, 키값의 비트 중 5개를 골라 쓰는 개념.
- "뽑을 비트 위치를 어떻게 고를 것인가"가 관건으로, 숫자 분석 함수에서 자릿수 단위로 분포를 분석했던 것처럼 비트 추출도 미리 키값들의 분포를 살펴 골고루 섞이는 비트 위치를 고르는 게 이상적이다. 
	- 즉 얘도 **별도의 비트 분포 분석 함수가 필요**하다.

```cs
public class BitExtractionHash
{
	// 키값의 이진 표현에서 지정된 비트 위치들만 뽑아 조합해 주소를 만든다. 
	public static int Search(int key, int[] bitPositions)
	{
		int address = 0;
		for (int i = 0; i < bitPositions.Length; i++)
		{
			int bit = (key >> bitPositions[i] & 1); // 해당 위치의 비트 값 추출
			address = (address << 1) | bit; // 추출한 비트를 순서대로 이어붙임
		}
		return address
	}
}
```
- `key >> bitPositions[i] & 1` : 키값을 오른쪽으로 밀어 원하는 비트를 최하위로 옮긴 뒤, `& 1`로 그 하나의 비트만 남김
	- 예시 : `13 >> 3` = `1101 >> 3` = `0101 >> 2` = `0010 >> 1` = `0001`, `0001 &1 = 1`
- `(address << 1 | bit)` : 지금까지 모은 주소를 왼쪽으로 한 칸 밀어 자리를 비운 뒤, 새로 뽑은 비트를 맨 오른쪽에 끼워 넣음. 여러 비트를 순서대로 붙이는 표준적인 방법.

- 예제
	- `key = 13(1101)`, `bitPositions = [3, 1, 0]`(뽑을 위치를 순서대로 지정)
	- `i = 0` : `13 >> 3`의 의미는 `1101 >> 3`, `0101 >> 2`, `0010 >> 1`, `0001`이 된다. 
		- `val >> n`은 "오른쪽으로 비트를 n번 밀라"는 의미.
		- `& 1`이므로 비트값은 `1`이 된다.
		- 이후  `(address << 1) | bit = 0 << 1 = 1` 
	- `i = 1` : `13 >> 1` : `1101 >> 1`, `& 1`로 `0`의 비트값을 뽑음.
		- `(address << 1) | bit)` = `10 | 0` = `10` = `2`(십진수)
	- `i = 2` : `13 >> 0` : `1`을 뽑고, `101` = `5`
	- 따라서 최종 주소는 `101`로, **오른쪽부터** 3번째 인덱스, 1번째 인덱스, 0번째 인덱스를 뽑은 `1, 0, 1`와 동일하다.


### 해싱에서 오버플로를 처리하는 방법

#### 오버플로 처리 방법 개념
- 아무리 좋은 해시 함수를 써도 **충돌을 완전히 없앨 수는 없음.** 
- **오버플로 처리는 충돌이 이미 일어났을 때, 그 키를 어디에 저장할 것인가**에 대한 전략이다. 크게 2가지 전략이 있다.
	1. **선형 개방 주소법** : 원래 테이블 배열 내에서 다른 빈 칸을 찾아 넣는 방식
	2. **체이닝** : 각 주소 자리에 여러 개를 매달 수 있는 별도 구조를 붙이는 방식
#### 선형 개방 주소법(Linear Open Addressing)
- 계산된 홈 주소가 이미 차 있을 때, 그 다음 칸부터 순서대로 **비어있는 칸**을 찾아 그 자리에 저장하는 방식.
- 테이블 자체만 사용하고 별도의 추가 구조가 필요하지 않지만, **한 번 충돌이 나면 주변 칸들이 연쇄적으로 채워지면서 특정 구간에 키들이 몰리는 `군집화Clustering`가 나타나기 쉽다.**

##### 선형 개방 주소법 알고리즘
1. 키값을 해시 주소에 넣어 홈 주소(시작 인덱스)를 반환한다.
2. 그 인덱스의 칸이 비어 있으면 검색 실패로 종료한다.
3. 그 칸의 값이 키값과 같으면 그 인덱스를 반환하고 종료한다.
4. 같지 않으면 다음 칸으로 이동한다. 테이블 끝이라면 처음으로 이동한다. 이후 2번부터 반복한다.
5. 한 바퀴를 다 돌아 홈 주소로 돌아왔다면 검색 실패로 종료한다.
##### 선형 개방 주소법 C# 구현
```cs
public class LinearProbingHashTable
{
	private int?[] table; // 각 칸은 값이 있으면 int, 비었으면 null
	private int tableSize;
	
	public LinearProbingHashTable(int tableSize)
	{
		this.tableSize = tableSize;
		table = new int?[tableSize];
	}
	
	private int Hash(int key) => key % tableSize;
	
	// 삽입 : 홈 주소부터 시작, 빈 칸이 나올 때까지 한 칸씩 이동
	public bool Insert(int key)
	{
		int idx = Hash(key);
		for (int i = 0; i < tableSize; i++)
		{
			int probe = (idx + i) % tableSize; // 테이블 끝을 초과하면 처음으로 순환
			if (table[probe] == null)
			{
				table[probe] = key;
				return true;
			}
		}
		return false; // 테이블이 꽉 차서 삽입 실패
	}
	
	// 검색 : 홈 주소부터 시작, 빈 칸을 만나거나 한 바퀴 돌 때까지 검색
	public bool Search(int key)
	{
		int idx = Hash(key);
		for (int i = 0; i < tableSize; i++)
		{
			int probe = (idx + i) % tableSize;
			if (table[probe] == null)
				return false; // 빈 칸 = 여기까지 삽입된 적 없음
			if (table[probe] == key)
				return true;
		}
		
		return false; // 테이블을 다 돌았으나 찾지 못함
	}
}
```
- `(idx + i) % tableSize`로 순환을 표현함.
- 검색 중 `null`을 만나면 즉시 실패로 끝낼 수 있다는 점이 체이닝과의 차이다.
	- "삽입 당시 이 칸이 비어 있었다면, 이후에 삽입된 키가 여기를 건너뛰어 그 뒤에 저장될 수 없다"는 삽입 로직의 성질(빈 칸을 만나면 저장)에 기대는 종료 조건.

```cs
if (table[probe] == null)
	return false; // 빈 칸 = 여기까지 삽입된 적 없음
```

>[!question] 
> `probe` 위치가 현재 `key` 외의, 다른 `key`에 의해 삽입될 수 있는 위치일 수 있지 않음? 어떻게 저기서 검색이 끝남?
- 실제로 다른 키가 들어갈 수 있는 위치이다.
- 그런데 **위 코드는 삭제가 없고, 빈 자리가 있다면 즉시 들어가는 방식**임. 검색 중에 `null`이었다는 건 이전에 해당 위치에 어떤 `key`도 삽입 시도가 없었다는 의미다.
- `Search(key)`는 해당 `key`에 대한 검색만 수행하고 있었고, 해시 위치에서 시작해서 1씩 증가하니까, **해시 위치보다 큰 값에서 `null`이 나타났다 = 해당 `key`의 삽입 시도가 아예 없었다 = `key`가 없다**라는 의미가 됨. 삽입 시도가 있었다면 해당 `null`이 바로 채워졌을 거니까. 
- **단, 삭제가 있다면 얘기가 달라진다.** 이때는 `null`이 아닌 `삭제됨Tombstone` 표시를 따로 둬서 검색은 `tombstone`을 건너뛰고 계속 진행하는 식으로 구현한다. 

#### 체이닝(Chaining)
- 테이블의 각 주소를 배열 칸이 아니라, 연결 리스트의 머리로 취급하는 방식. 
- 같은 주소로 계산된 키들은 모두 그 버킷에 매달린 연결 리스트에 순서대로 추가된다.
- 꽉 차는 일이 없고 군집화 문제도 없지만, 연결 리스트 노드를 위한 추가 메모리가 필요하며 검색 시 해당 리스트를 순차 검색해야 함.

##### 체이닝 알고리즘
1. 키값을 해시 함수에 넣어 주소(버킷 인덱스)를 계산
2. 그 버킷이 가리키는 연결 리스트의 첫 노드부터 순회 시작
3. 현재 노드의 값이 키값과 같으면 노드 반환 후 종료
4. 리스트 끝`null`에 도달하면 실패 반환

##### 체이닝 C# 구현
```cs
public class Node<T>
{
	public T data;
	public Node<T> Next;
	
	public Node(T data)
	{
		Data = data;
	}
}

public class ChainingHashTable
{
	private Node<int>[] buckets;
	private int tableSize;
	
	public ChainingTableSize(int tableSize)
	{
		this.tableSize = tableSize;
		buckets = new Node<int>[tableSize];
	}
	
	private int Hash(int key) => key % tableSize;
	
	// 삽입 : 계산된 버킷의 리스트 맨 앞에 새 노드를 추가
	public void Insert(int key)
	{
		int idx = Hash(key);
		Node<int> newNode = new Node<int>(key)
		{
			Next = buckets[idx];
		}
		buckets[idx] = newNode;
	}
	
	// 검색 : 버킷 계산 후, 그 안의 연결 리스트를 순차 검색
	public bool Search(int key)
	{
		int idx = Hash(key);
		Node<int> current = buckets[idx];
		
		while (current != null)
		{
			if (current.Data == key)
				return true;
			current = current.Next;
		}
		return false;
	}
}
```
- `buckets` 배열의 각 칸은 연결 리스트의 `head`노드, 혹은 `null`을 가리킴.
- `Insert`에서 리스트 맨 앞에 추가하는 이유는 $O(1)$로 삽입을 끝내기 위함. 

## 생각해볼 만한 질문들

1. **순차 검색에서 정렬되지 않은 자료와 정렬된 자료의 시간복잡도 차이?**
	- 공식은 $O(n)$으로 두 방식이 동일하다.
	- 단, 정렬된 경우는 조기 종료 조건을 넣을 수 있다. 
		- 오름차순 기준, 찾고자 하는 값이 이미 현재값보다 크다면 아예 없다로 종결 가능.

2. **색인 순차 검색과 이진 검색은 둘 다 정렬을 전제로 하는데, 왜 시간복잡도가 다른가?**
	- **둘 다 정렬된 배열을 전제**로 함. 
	- 색인 순차 검색 : $O(\sqrt{n})$ 
		- 전체 자료 크기가 n, 블록 크기가 b일 때 
		- 색인 테이블 검색 비용 : `n / b`
		- 블록 내 검색 비용 : `b`
		- 검색 비용이 최소가 되는 지점이 $b = \sqrt{n}$이며 이때의 비용이 $2\sqrt{n}$이다. 
	- 이진 검색 : $O(log\,n)$
		- 탐색 범위가 절반씩 줄어들면 이런 표현을 쓴다.

3. **배열 이진 검색과 이진 트리 검색은 시간복잡도 공식이 $O(log\,n)$으로 같아 보이는데, 실제 전제조건에 어떤 차이가 있는가?**
	- 이진 검색 : "정렬된 배열"
	- BST 검색 : 트리에 넣는 순서가 중요하다. 균형 트리여야 $O(log\,n)$이 나오며 편향이라면 $O(n)$이 나옴.

4. **해싱 - 동거자와 충돌의 차이**
	- 동거자는 해시에서 같은 인덱스를 공유하는 키값들.
	- 충돌은 동거자들에 해시함수를 적용시켜 해시 테이블에 넣으려고 할 때 발생하는 사건.

5. **계산 함수, 승산 함수, 접지 함수, 비트 추출 함수는 "키값 → 주소" 변환이라는 목적은 같다. 각각 어떤 계산 방식(산술 연산 / 값 분해·재조합 / 비트 선택)을 쓰며, 이 중 사전에 별도 분석이 필요한 함수는 무엇인가?**
	- 산술 연산 기반 : 계산 함수, 승산 함수
	- 쪼개서 조합하기 : 접지 함수(이동(그대로), 경계(뒤집기))
	- 비트 선택 : 비트 추출 함수
	- 사전 별도 분석 필요 - 숫자 분석 함수와 비트 추출 함수. 자릿수의 숫자 갯수나 비트의 고른 분포를 파악해야 하므로 별도의 분석 함수가 필요하다.

6. **선형 개방 주소법과 체이닝은 충돌을 각각 어떻게 처리하며, 그 결과 어떤 문제가 생기는가?**
	- 선형 개방 주소법 
		- 충돌 발생 시 인덱스를 1씩 증가시켜 테이블 전체를 순회하며 빈 값에 채워넣음
		- 군집화 문제가 발생할 수 있다 - 인덱스를 1씩 순회하기 때문에 특정 구간에 키가 몰리는 현상.
	- 체이닝
		- 테이블의 원소를 연결 리스트로 만들고 충돌이 발생하면 계속 이어붙이는 로직
		- 자체에 포인터를 가지니까 선형 개방 주소법보다 차지하는 공간이 많아질 거임

7. **적재 밀도가 높아지면 선형 개방 주소법과 체이닝 각각에 어떤 영향을 주는가?**
	- 적재 밀도 
		- 실제로 저장된 레코드 수를 해시 테이블이 가진 전체 버킷 수로 나눈 비율.
		- 쉽게 말하면 테이블의 사용된 공간이다.
	- 적재 밀도가 높아지면
		- 선형 개방 주소법 : 인덱스를 하나씩 순회하므로, 빈 공간이 없을수록 삽입 시간이 길어진다.
		- 체이닝 : "테이블이 꽉 찬다"는 개념은 성립하지 않는다. 대신, 특정 인덱스에 데이터들이 쌓이기 때문에 뒤로 밀려있는 데이터를 찾기 위해선 하나씩 넘어가야 하므로 임의 접근보다 더 시간이 오래 걸릴 거임.
