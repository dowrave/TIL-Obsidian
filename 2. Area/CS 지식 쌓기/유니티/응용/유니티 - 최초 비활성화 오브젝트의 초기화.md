#유니티 

## 상황
- 일반적으로 컴포넌트의 초기화는 `Awake`에서 이뤄지는 경우가 많음. 
	- (별도로 `[SerializeField]`로 빼두고 설정할 게 아니라면)

```cs
private void Awake()
{
	_toggle = GetComponent<Toggle>();
	_toggle.onValueChanged.AddListener(HandleValueChanged);
	ButtonSoundUtility.AddClickSound(_toggle);
}
```

- 그런데 해당 스크립트가 처음부터 비활성화된 상태라면, `Awake`는 오브젝트가 활성화된 시점에 최초 1회만 동작하므로, `Awake` 동작이 이뤄지지 않게 된다.
- 이 상황에서 다른 스크립트에서 비활성화된 오브젝트에 접근했고, 위 예제의 `Toggle`을 사용하는 스크립트에 접근하면 `NullReferenceException`에 접근하게 됨.

## 해결
- 크게 2가지 해결책이 있음.

### 1. `[SerializeField] private`으로 참조 사전 등록
```cs
[SerializeField] private Toggle _toggle;
```
- 타이밍 문제를 생각하지 않아도 되기 때문에 깔끔하다. 
- 하지만 **같은 오브젝트의 다른 컴포넌트를 인스펙터로 참조하는 게 컨벤션 상으로 권장되는 개념은 아님**

여러 단점을 결합해서 보면 더 좋을 것 같음. 

>[!note]
>- 같은 오브젝트일 경우, 해당 컴포넌트를 갖고 있을 가능성이 높음이 보장되고, 별도의 `[SerializeField]`로 인스펙터에 일일이 표기하면 더 중요한 정보가 묻힐 수 있기 때문에 `GetComponent<T>()`로 캐싱해둔다는 이야기.

1. 참조가 깨질 가능성이 적음
	- 같은 오브젝트 참조
		- **해당 컴포넌트가 존재하는 게 구조적으로 보장**되는 경우가 많다.
	- 자식 / 타 오브젝트 참조
		- 하이어라키 구조의 변경, 오브젝트 삭제 / 이동 등 **깨질 가능성이 더 높음.**

2. 같은 오브젝트의 경우, 아래의 단점들이 발생함.
	- **인스펙터가 지저분해진다**
		- 같은 오브젝트의 `RectTransform, Image, CanvasGroup` 등등을 모두 인스펙터의 필드로 노출해버리면, 의미 있게 봐야 할 참조들이 상대적으로 인스펙터에서 묻히는 현상이 있음. 
		- 명시성이 너무 과할 필요는 없다. 
	- 드래그 & 드롭 자체가 불필요한 수작업
		- `this.GetComponent<T>()`로 100% 찾아지는 대상이므로, 굳이 사람 손을 거치게 할 필요가 없음
	- 프리팹 복제 / 재사용 시 실수 유발 지점 증가
		- 드래그 & 드롭으로 결정하는 부분이므로 휴먼 에러가 발생할 가능성이 높다는 얘기임. 

### 2. 별도의 셋업 메서드를 구현
```cs
private void Awake()
{
	EnsureSetup();
}

public void Initialize(SaveSlotMetadata metadata = null)
{
	EnsureSetup();
	// ...
}

// Initialize, Awake 양쪽에 두는 셋업 메서드
// 최초에 비활성화된 경우 Awake에서 동작하지 않을 수 있기 때문에 별도의 메서드로 둔다.
private void EnsureSetup()
{
	// 1번만 동작해야 함
	if (_isSetup) return;

	_toggle = GetComponent<Toggle>();
	_toggle.onValueChanged.AddListener(HandleValueChanged);
	ButtonSoundUtility.AddClickSound(_toggle);

	_isSetup = true;
}
```
- `Awake`가 동작하지 않는 상황이 있을 수 있기 때문에, `Awake`의 동작을 별도의 메서드로 빼두고 `Initialize`와 `Awake` 양 쪽에 넣는다. 
- 1회만 실행돼야 하므로 플래그도 설정해줌.

### 3. 아예 다른 접근 : CanvasGroup.alpha 설정으로 투명화만
- **게임 오브젝트는 계속 활성화 상태를 유지하되, 투명한 상태로만 만드는 개념**이다.
- 계속 켜져 있기 때문에 `Awake` 등에 의한 타이밍 문제를 해결할 수 있지만, `Update`나 `LayoutGroup` 재계산 등의 비용이 계속 들 수 있기에 갯수가 많거나 무거운 UI보다는 **소수의 팝업 / 패널류에 더 적합**하다.

>[!note]
>- 이 접근법은 되게 괜찮아 보인다. 대부분의 상황에서 원하는 건, **현재 사용하고 있지 않은 패널이 투명한 상태를 유지하는 것**이기 때문.
>- 활성화 관련해서는 생명주기라든가, 이벤트 구독/해제라든가, 애니메이션이라든가 등등등 생각할 게 너무 많아지니까 '이것만 구현하려고 했는데 저것까지 생각해야 하네?'같은 상황이 꽤 자주 발생해서 시간이 오래 끌리곤 했다.
